# ADR 0003: NUMERIC(12,4) Fixed-Point Storage vs. float64 Python Computation

## Status

Accepted

## Context

Financial market data systems face an inherent conflict between precision integrity and analytical execution speed:
1. **Precision Integrity**: Indian equity markets operate with tick sizes of `0.05` and `0.01` INR. Corporate actions (such as 1:2 bonus splits or dividend subtractions) and Volume-Weighted Average Prices (VWAP) introduce sub-tick fractional decimals. Standard IEEE 754 double-precision floating-point numbers (`float64`) suffer from binary representation artifacts (e.g. `0.1 + 0.2 = 0.30000000000000004`). In financial accounting, ledger reconciliation, order matching, and deterministic backtesting, subtle floating-point inaccuracies accumulate into non-deterministic drift, order fill discrepancies, and test flakiness.
2. **Computational Performance**: In contrast to storage and ledger accounting, Python data science runtimes (Pandas, Polars, NumPy) and technical indicator libraries (`pandas_ta`, TA-Lib) rely heavily on vectorized C/SIMD instruction sets that natively consume contiguous arrays of 64-bit IEEE floating-point numbers (`float64`). Requiring Python to evaluate technical indicators using arbitrary-precision decimal objects would degrade backtesting speed by orders of magnitude.
3. **Storage & Serialization Boundaries**: At database and inter-service boundaries (PostgreSQL/TimescaleDB, Go REST/WebSocket responses, and gRPC payloads), the application requires an unambiguous, loss-free canonical representation of price.

## Decision

We establish a strict dual-representation architecture:

1. **Database Storage (`NUMERIC(12,4)`)**:
   - All physical candle tables (`candles_1s`, `candles_1m`), continuous aggregates, order records, and trade logs store prices using PostgreSQL's `NUMERIC(12,4)`.
   - `NUMERIC(12,4)` guarantees exact base-10 precision with 8 integer digits (supporting prices up to `99,999,999.9999`, easily accommodating the highest-priced NSE equities such as MRF at ~₹140,000) and 4 decimal places for sub-tick accuracy.

2. **Go Domain Models (`pgtype.Numeric` / Strings)**:
   - Within the Go backend (`internal/store/candles`), the canonical `Candle` struct stores OHLC prices as `pgtype.Numeric`.
   - JSON serialization at API boundaries transmits decimals formatted accurately without IEEE float conversion.

3. **Isolated Boundary Conversion Helper**:
   - Conversions between `NUMERIC(12,4)` / `pgtype.Numeric` and native `float64` are strictly centralized in a single Go package helper (`internal/store/candles/numeric.go`).
   - Ad-hoc conversions, inline bit manipulation, or unverified casts elsewhere in the codebase are prohibited.
   - Any price conversion from `float64` explicitly validates against `NaN` and `Inf`.

4. **Python Indicator Vectorization (`float64`)**:
   - The Python strategy worker pool loads OHLCV columns directly into `float64` arrays for vectorized computation (`generate_signals(df)`).
   - Signals generated by user strategies are discrete integers (`1` BUY, `-1` SELL, `0` HOLD) and do not mutate the canonical ledger prices.
   - Any monetary accounting or paper-trade execution fills calculated from signal events are mapped back to exact fixed-point decimals upon persistence in PostgreSQL.

## Consequences

### Positive
- **Deterministic Accounting**: Zero float rounding drift in database tables, range queries, and ledger balances across repeated test cycles.
- **Maximized Compute Speed**: Python vectorization retains full native SIMD performance using `float64` dataframes.
- **Architectural Clarity**: All conversions happen in exactly one monitored location with explicit range and validity checking.

### Negative
- Go code interacting with analytical libraries must explicitly invoke `NumericToFloat64` or `Float64ToNumeric` at boundaries.
